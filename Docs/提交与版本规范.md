# 提交与版本规范

## 什么时候可以提交

三条都满足才提交：

1. Unity 里编译通过，Console 里没有红字。
2. Test Runner 的 EditMode 全绿（Window → General → Test Runner → EditMode → Run All）。
3. 每个新文件旁边都有它的 `.meta`。新加文件之后要切到 Unity 窗口让它刷新一次，`.meta` 才会生成。

## 一次提交放什么

- 一次提交只做一件事。日志是一次，状态机是一次，不混在一起。
- 搬和改分开：先原样搬过来提交一次，再改。
- 代码、它的测试、它的手册，放在同一次提交里。
- `.meta` 跟着它的文件一起提交，不能落下。

## 提交说明怎么写

格式：`类型(范围): 一句话`

| 类型 | 什么时候用 |
|---|---|
| `feat` | 加了新东西 |
| `fix` | 修了一个错 |
| `refactor` | 改了结构，行为没变 |
| `test` | 只动了测试 |
| `docs` | 只动了文档 |
| `chore` | 工程设置、包、工具 |

- 范围是模块名，小写：`log`、`fsm`、`handle`、`flow`、`runtime`、`project`。只动文档时可以不写范围。
- 一句话用英文，动词开头，首字母小写，结尾不加句号，不超过 72 个字符。说做了什么，不说怎么做的。
- 需要解释原因时，空一行再写正文，正文可以用中文。

例子：

```
feat(log): add logging pipeline with file sink and crash reports
feat(fsm): add flat state machine with transition table builder
feat(handle): add generational handles and allocator
docs: add coding conventions
fix(log): keep error stack trace when message repeats
```

## 分支

- `main`：永远能编译、能跑。
- `dev`：日常在这里干活。一块东西做完、上面三条都满足，合进 `main`。

## 版本号

格式：`主.次.修`，例如 `0.3.1`。

| 哪一位 | 什么时候加 1 |
|---|---|
| 主 | 发售那天从 0 变成 1 |
| 次 | 多出一样能玩到或能用上的东西。加了之后"修"归零 |
| 修 | 只修错，没加东西 |

- 发售之前主版本一直是 0。
- **版本号只有一个出处：工程根目录的 `version.txt`**，里面只有一行，例如 `0.1.0`。改版本号只改这一个文件。
- Unity 的 Player Settings 里那一格 Version 不用手改。编辑器会自己把 `version.txt` 抄过去，时机有三个：载入代码之后、点运行之前、打包之前。日志文件开头和崩溃包里写的版本，读的就是抄过去的这个值。
- `version.txt` 写法不对（不是三个数、带了字母、带了前导零）：Console 里报红字；打包直接失败。
- 抄过去之后 `ProjectSettings/ProjectSettings.asset` 里也会跟着变一行，它和 `version.txt` 放在同一次提交里。
- 打一个版本的三步：改 `version.txt`；提交，说明写 `chore(project): bump version to 0.2.0`；在 `main` 上打标签 `v0.2.0`。

现在 `version.txt` 里是 `0.1.0`。第一个标签 `v0.1.0` 定在日志、状态机、句柄这三样地基合进 `main` 的时候。
